# B. Feature delivery

**Start with:** a desired user/business outcome, current system evidence, scope and authorization. A request to design first ends at the design handoff; an implementation request permits ordinary reversible delivery decisions.

1. **Read and map the current behavior.** Trace the relevant request → business operation → storage/external effect → response. Read domain docs, schema/contracts, tests and accepted decisions. Record just enough to distinguish existing capability, defect and proposed behavior.
2. **Resolve the next consequential unknown.** For each gap ask privately what answer changes which decision and what guessing could cost. Read existing answers first. Ask only unresolved material meaning/security/privacy/data-loss questions; defer unrelated future choices. Use explicit reversible assumptions for low-consequence gaps. Work on independent authorized tasks while waiting.
3. **Make acceptance concrete.** Write representative input/state → operation → expected effect examples in existing notes/tests. Define units, identity, roles, temporal boundaries, unknowns and errors where they affect this feature. Keep disagreements unresolved rather than invent policy. If existing acceptance already covers them, reuse it.
4. **Choose the smallest credible design change.** Inspect affected boundaries. Compare alternatives only where consequence warrants it; preserve necessary transactions, durability and isolation. For substantial flow changes show one useful editable diagram, label current/proposed and walk an example/failure through it. Identify compatibility, rollout/rollback, operating owner and a concrete revisit trigger where relevant.
5. **Deliver a vertical slice.** Choose an observable path through the affected boundaries, not infrastructure foundations alone. Name actual files after reading them, expected behavior, interfaces/dependencies and checks. Implement when authorized; a plan-only/design-only request stops at its requested result. Do not insert a new permission checkpoint merely because the plan is written.
6. **Verify and review the increment.** Execute meaningful domain, real changed integration and critical-flow checks. Check diff/scope and maintainability. Fix authorized failures; if implementation reveals mistaken accepted behavior, explain the change and resolve its consequence before depending on it. A missing environment remains Not verified.
7. **Carry the result forward.** Report what is demonstrated, what remains and the next useful increment. When the request includes full delivery, continue remaining authorized increments. Do not end at a first-slice plan if the user asked for implementation.

**Useful finish:** the requested behavior and consequential constraints are accounted for in the delivered artifact and evidence; unresolved issues and operational limits are visible. A design-only handoff contains implementable choices and proposed checks, not fictional test results.

**Load only as needed:** discovery/requirements/acceptance methods at steps 2–3; architecture/visuals/contracts for step 4; delivery/Python/implementation for step 5; review/evidence at step 6. The worked extraction walkthrough in `walkthrough.md` demonstrates the handoffs and a corrected decision.
