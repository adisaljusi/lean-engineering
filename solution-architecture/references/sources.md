# Foundations and source limits

These guides are original, attributed synthesis and original examples. They do not quote books, reproduce diagrams, claim access to unavailable full texts, or assign chapter/page numbers. Editions are named only where relevant; this is not a claim to use the latest edition. Public author/catalog/documentation links are further reading, not proof that a model learned the method.

| Foundation | Source identity | Decision translated into practice |
|---|---|---|
| Clean Architecture | Robert C. Martin, *Clean Architecture: A Craftsman's Guide to Software Structure and Design* | Policy dependencies point away from volatile adapters; add boundaries where change/testing warrants them, not layers for their own sake |
| DDIA | Martin Kleppmann, *Designing Data-Intensive Applications*, first edition (2017); [author-maintained references](https://github.com/ept/ddia-references) | Access patterns, consistency/transactions, replication/partitioning cost, batch/stream recovery |
| Architecture fundamentals | Mark Richards and Neal Ford, *Fundamentals of Software Architecture* | Quality scenarios and trade-offs rather than checklist-driven topology |
| Difficult architecture choices | Neal Ford, Mark Richards, Pramod Sadalage and Zhamak Dehghani, *Software Architecture: The Hard Parts* | Coupling, ownership, data boundaries and consequences of distribution |
| Services | Sam Newman, *Building Microservices*; *Monolith to Microservices*; [author's books](https://samnewman.io/books/) | Independent ownership/deployment, operational costs and incremental migration; modular monolith remains credible |
| Integration | Gregor Hohpe and Bobby Woolf, *Enterprise Integration Patterns*; [author site](https://www.enterpriseintegrationpatterns.com/) | Request/reply, routing, transformation, correlation, delivery, retries and poison-message responsibility |
| Domain modeling | Eric Evans, *Domain-Driven Design: Tackling Complexity in the Heart of Software* | Shared meaning, identity, lifecycle, ownership and invariants; not a class per noun |
| Enterprise application patterns | Martin Fowler (with contributors), *Patterns of Enterprise Application Architecture*; [author catalog](https://martinfowler.com/eaaCatalog/) | Transaction script, unit of work and data mapper selected by actual persistence/domain needs |
| Object design | Erich Gamma, Richard Helm, Ralph Johnson and John Vlissides, *Design Patterns: Elements of Reusable Object-Oriented Software* | Recognize substitution/creation/coordination problems before introducing a pattern; a Python function may suffice |
| API systems | James Gough, Daniel Bryant and Matthew Auburn, *Mastering API Architecture: Design, Operate, and Evolve API-Based Systems* | Consumer contracts, failure boundaries, evolution and operations |
| API lifecycle | Mehdi Medjaoui, Erik Wilde, Ronnie Mitra and Mike Amundsen, *Continuous API Management: Making the Right Decisions in an Evolving Landscape*; [coauthor material](https://github.com/dret/lectures/blob/master/entel-2019/toc.html) | Ownership, lifecycle, deprecation/observability and governance proportionate to the organization |
| Human communication | Jacqui Read, *Communication Patterns: A Guide for Developers and Architects* | Audience/question-led views and understandable decision communication; not the source of broker delivery guarantees |
| Algorithms/data structures | Thomas H. Cormen, Charles E. Leiserson, Ronald L. Rivest and Clifford Stein, *Introduction to Algorithms*; [Python collections](https://docs.python.org/3/library/collections.html) | Workload/cardinality, runtime/memory cost, standard library/database support and measured bottlenecks |
| Practical Python | [Python documentation](https://docs.python.org/3/), [packaging guide](https://packaging.python.org/), [OpenAPI](https://spec.openapis.org/oas/latest.html) | Language/library contracts, resource ownership, concurrency, packaging and API schemas |
| Visuals | Simon Brown's [C4 model](https://c4model.com/), [Mermaid source/docs](https://github.com/mermaid-js/mermaid) | Choose a view by question, validate syntax and inspect meaning/readability |

“API Architecture” alone is an ambiguous title/topic in the request. No author, edition or quotation is invented for it. The guides cover API architecture through the identified *Mastering API Architecture*, *Continuous API Management* and OpenAPI sources instead. Confirm a specific title before attributing more precise claims.

The remaining entries identify established works for attribution/further detail; no claim is made that their full text or latest editions were retrieved in this run.
